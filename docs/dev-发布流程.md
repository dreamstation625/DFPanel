# dev 与正式版本发布流程

本次安全及运行逻辑修复先进入 `dev`，正式目标版本为面板 / Agent `0.0.3`。用户验证预发布版本后再合并 `main`；本次不合并 `main`。

## 自动构建规则

两条 workflow 在 `dev`、`main` 推送时运行，也可手动选择这两个分支执行。所有源码推送都会构建，不再只监听版本文件变化。tag 不触发发布，手动选择其它分支会失败。

| 分支 | Release | 镜像 |
| --- | --- | --- |
| dev | `v0.0.3-pre.<提交时间戳>.g<提交前12位>`，Pre-release，Latest=false | `0.0.3-pre.<提交时间戳>.g<提交前12位>` 和 `pre` |
| main | `v0.0.3`，正式发布，Latest=true | `0.0.3` 和 `latest` |

`VERSION` 和 `VERSION.agent` 始终保存正式目标版本 `x.y.z`。两条 workflow 使用同一版本脚本，预发布版本按提交时间戳和 SHA 生成，重复运行同一提交不会产生不同版本。已有 Release tag 指向其它提交时阻止发布，避免覆盖之前的正式版本。

发布前运行版本策略测试、Go 测试、Go vet、前端类型检查和构建；任何必需检查失败都会阻止发布。原有 Linux / Windows / macOS 二进制矩阵和 Agent 全平台包保留。Docker 构建参数将实际预发布版本注入面板、独立 Agent、内置 Agent 和内置版本清单。

GitHub Environment `DOCKERHUB` 需要允许 `dev` 分支使用现有凭据；如果此前只允许 `main`，需在仓库设置中加入 `dev`。workflow 不自动修改仓库设置。

## Release 升级说明

版本专用说明保存在 `docs/release-notes/<正式目标版本>.md`。发布时按 `VERSION` 读取，并放在自动生成的更新日志之前；同一目标版本的 `dev` 预发布和 `main` 正式发布共用该说明。没有对应文件的版本只生成更新日志，不会继承旧版本提示。

`0.0.3` 的说明要求面板与所有 Agent 同步升级。修改说明后只影响后续发布流程；已发布的 Release 需要在 GitHub 单独编辑。面板点击“检测版本”会显示所选发布通道的 Release 说明，后台检测和 Agent 检测不会弹窗。

## 预发布验证

1. 等待 `dev` 对应提交的 Release、Docker 两条 Actions 全部成功。
2. 测试安装时使用该提交的精确版本；`pre` 是移动标签，测试记录应写下精确版本和提交 SHA。
3. 备份面板与 Agent 数据目录，再同步升级两端。新版拒绝旧签名，旧登录会话需要重新登录。HTTP 继续可用，建议 HTTPS。
4. 验证初始化和登录 / 注销、旧凭据拒绝、Agent 连接与重连、配置应用 / 启停、断线后的积压执行、历史回滚、失败恢复、节点删除及日志轮转。
5. 如果需要面板生成预发布 Agent Docker 安装命令，设置 `DFPANEL_AGENT_IMAGE=dreamstation625/dfpanel-agent:<精确预发布版本>`；默认 Agent 镜像仍是正式版 `latest`。二进制安装使用同一 Release 的 Agent 全平台包。

本次修复对应关系及升级边界见 [安全与运行逻辑修复](安全与运行逻辑修复-2026-10-10.md)。第 9 项按要求未实施。

## 验证通过后

确认测试所用提交，再将 `dev` 合并到 `main`（推荐通过 PR）。只合入已验证内容；有新提交时先重新验证。合并后的 `main` 推送触发正式 Release 与镜像构建，版本文件无需去掉后缀。

下一次正式发布之前，应在 `dev` 提升相应目标版本。正式版本 tag 已存在且属于其它提交时，校验会拒绝重用该版本号。
