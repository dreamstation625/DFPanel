## 优先修复的问题

### 1. [P1] 公开初始化存在竞态，可同时创建多个管理员

位置：[auth.go](E:/Code/git/DFPanel/internal/handler/auth.go:43)、[公开路由](E:/Code/git/DFPanel/internal/router/router.go:44)。证据：专项复现。

初始化先 Count 再计算 bcrypt、最后 Create，没有覆盖整个过程的锁、事务性单例约束或一次性初始化凭证。尚未初始化时两个不同用户名的请求可以同时看到 count=0，随后都创建 admin。专项测试同步两个请求的读取阶段，实际得到两个 HTTP 200 和两条管理员记录。已经初始化的正常状态不受这次竞态影响。

建议：为初始化增加原子单例约束，并在事务内完成状态检查和创建；对首次设置增加部署端的一次性凭证或限制入口，避免任意访客先占管理员身份。

### 2. [P1] Agent 签名可跨接口和正文重放，且签名参数会进入 URL 日志

位置：[签名](E:/Code/git/DFPanel/internal/proto/proto.go:138)、[验证](E:/Code/git/DFPanel/internal/proto/proto.go:146)、[请求构造](E:/Code/git/DFPanel/internal/agent/client.go:40)、[鉴权](E:/Code/git/DFPanel/internal/handler/agent.go:40)、[请求日志](E:/Code/git/DFPanel/internal/router/router.go:28)。证据：专项复现。

HMAC 只覆盖 nodeKey 和时间戳，没有覆盖 HTTP 方法、路径、正文、实例身份，也没有 nonce 去重。获取一条完整已签名 URL 的人，在五分钟窗口内可以重用它读取配置、领取指令、伪造状态或建立新连接。测试把 configs 请求的鉴权串原样用于 heartbeat，并重复提交不同正文，两次都成功修改了数据库。

Agent 将完整鉴权串放在 URL，Gin 的默认请求日志也记录查询串；因此即使使用 HTTPS，访问日志仍可能提供可重放凭据。这里不需要恢复 Secret。

建议：签名绑定方法、规范化路径、正文摘要、实例身份和一次性 nonce；鉴权值改放请求头，日志脱敏；Agent 与面板使用 HTTPS/WSS。时间窗口检查只能限制重放时段，不能替代去重。

### 3. [P1] 一个 Agent 可以伪造另一个 Agent 的 WebSocket 指令回执

位置：[pending 表](E:/Code/git/DFPanel/internal/agenthub/hub.go:28)、[读循环](E:/Code/git/DFPanel/internal/agenthub/hub.go:246)、[回执匹配](E:/Code/git/DFPanel/internal/agenthub/hub.go:276)、[可预测指令 ID](E:/Code/git/DFPanel/internal/handler/exec.go:65)。证据：专项复现。

Hub 仅使用 env.ID 查找全局等待项，未记录、检查预期 AgentID。已鉴权的 Agent 2 只要猜到 `cmd-N`，就能给正在等待 Agent 1 的操作发送成功或失败结果。真实本机 WebSocket 测试中，Hub.Send(Agent 1) 接受了 Agent 2 的伪造成功响应。可能错误更新指令、配置版本与页面状态；这不意味着能直接把指令发到其他 Agent 执行。

建议：pending 保存目标 AgentID；回执处理传入当前连接身份并校验 Agent、消息类型和命令状态。随机 ID 可以降低猜测概率，但不能代替归属校验。

### 4. [P1] 重置 Agent 密钥不会撤销已有连接

位置：[ResetToken](E:/Code/git/DFPanel/internal/handler/agents.go:195)、[WebSocket 接入](E:/Code/git/DFPanel/internal/handler/agent.go:353)。证据：专项复现。

重置只更新数据库密钥和 offline 标记，没有断开 Hub 内已鉴权连接。旧连接无需再次签名，仍可收取之后的配置和控制指令、上报状态。测试重置后通过旧连接修改 hostname 成功，Hub.Online 仍返回 true。用于处理密钥泄露时，重置因此不能完成撤销。

建议：重置和删除身份时主动断开对应连接并清理等待项；为连接绑定凭据代次，阻止重置过程中使用旧凭据建立或继续使用连接。

### 5. [P1] Agent WebSocket 有多个并发写入者

位置：[定时心跳](E:/Code/git/DFPanel/internal/agent/agent.go:117)、[指令回复及 Pong](E:/Code/git/DFPanel/internal/agent/agent.go:144)。证据：代码确认；未进行长期碰撞压力测试。

心跳协程和指令处理循环都直接调用 conn.WriteJSON，没有写锁或统一发送队列。Gorilla WebSocket 明确要求每个连接最多有一个并发写入者；心跳与回执/Pong 重叠可导致数据竞争、写入错误或 panic。Agent 没有保护该协程的恢复逻辑，可能整个退出。

建议：所有 JSON 写操作进入单一发送协程，或共享互斥锁；统一写超时与错误处理。[官方并发契约](https://pkg.go.dev/github.com/gorilla/websocket#hdr-Concurrency)。

### 6. [P1] 离线排队的指令在恢复 WebSocket 后可能一直不执行

位置：[Run](E:/Code/git/DFPanel/internal/agent/agent.go:81)、[pollOnce](E:/Code/git/DFPanel/internal/agent/agent.go:153)、[Hub.Attach](E:/Code/git/DFPanel/internal/agenthub/hub.go:55)。证据：代码确认。

Run 先进入阻塞的 serveWS，只有长连接退出后才 pollOnce。面板 Attach 也不会主动发送数据库中的 pending 指令。因此 Agent 离线时排队的应用/停止/清理指令，如果上线后直接成功建立并持续保持 WS，会一直留在 pending，直到连接再次中断。界面承诺的「上线后自动执行」不成立；排队的 unassign 还会阻止删除 Agent。

建议：建立连接前或连接后执行统一的积压领取/发送流程，保证新指令与积压指令按顺序执行，并防止重复领取。

### 7. [P1] 轮询领取普通指令后发生断线或崩溃，会永久丢失指令

位置：[Commands](E:/Code/git/DFPanel/internal/handler/agent.go:252)、[pollOnce](E:/Code/git/DFPanel/internal/agent/agent.go:159)。证据：专项复现。

服务器在响应实际送达之前就标记 sent；Agent 执行完只尝试上报一次。下一次查询只找 pending，以及超时 sent 的 unassign。apply/start/stop/restart 等普通指令没有重投递或结果补报机制。专项测试领取 stop 后模拟无回执，把 sent_at 提前一小时，仍无法再次领取。

建议：建立指令租约、超时重投递和持久化执行去重；区分已领取、已执行、结果待确认。结果补报和重投递必须一起设计，避免为补救丢失而重复重启服务。

### 8. [P1] 本机 frps 应用配置缺少 Agent 模式已有的验证和自动恢复

位置：[本机 Apply](E:/Code/git/DFPanel/internal/handler/server.go:288)、[写配置](E:/Code/git/DFPanel/internal/frp/process.go:121)、[进程重启](E:/Code/git/DFPanel/internal/frp/process.go:199)、[Agent 对照](E:/Code/git/DFPanel/internal/agent/apply.go:74)。证据：代码确认。

本机 Apply 直接覆盖当前配置，再 Kill 旧进程并 Start。没有 frps verify、配置备份、启动后健康检查或自动回滚。Start 成功创建进程即返回，即使新进程随后因无效字段/证书路径退出，Apply 仍可提示配置已生效。写入也不是原子替换，写中断可能破坏当前配置。

建议：与 Agent 共用「暂存 → verify → 备份 → 切换 → 重启 → 确认可用 → 失败恢复」流程。本次没有对实际 frps 制造故障，因此未宣称复现了真实服务中断。

### 9. [P1/条件性] 下载 frp 后在校验可信来源之前执行文件

位置：[EnsureFRPBinary](E:/Code/git/DFPanel/internal/distrib/download.go:201)、[版本查询](E:/Code/git/DFPanel/internal/distrib/download.go:214)、[Agent 下载](E:/Code/git/DFPanel/internal/agent/client.go:184)。证据：代码确认。

镜像包解压后没有对可信发布清单做 SHA256 校验，直接执行二进制查询版本；查询失败又被忽略，文件仍可作为下载成功保留。可配置镜像源被篡改、使用 HTTP 遭受中间人攻击，或上游文件损坏时，可能执行恶意文件或污染缓存。打印正确版本字符串不是来源认证。

建议：从可信来源取得预期摘要/签名，完成校验后才执行；同平台版本检查错误应明确失败，跨平台不能执行时只跳过执行检查，不能跳过内容校验；提取到临时文件后原子加入缓存。该风险依赖下载源或链路失信，未发现无需管理员权限即可直接更改镜像源的接口。

## 功能与条件性安全问题

### 10. [P2] 多个接口把 URL 的字符串 ID 当成 SQL 条件

位置：[Agent Get](E:/Code/git/DFPanel/internal/handler/agents.go:47)、[节点 Update](E:/Code/git/DFPanel/internal/handler/node.go:108)、[安装命令查询](E:/Code/git/DFPanel/internal/handler/install.go:50)、[访问端 Update](E:/Code/git/DFPanel/internal/handler/visitor.go:79)。证据：专项复现。

`DB.First(&record, c.Param("id"))` 遇到非数字字符串时会把它当作原始 SQL 条件。测试 ID `0 OR 1=1` 成功读到第一条 Agent 记录，包含 Secret。正式路由有 JWT，所以这是登录后的注入和对象选择风险，不能表述为未登录读取数据。其他类似调用应一起审查。

建议：统一解析正整数 ID，明确拒绝 0、负数及非数字输入，再按数值主键查询，或使用 `Where("id = ?", id)`。[GORM 官方说明](https://gorm.io/docs/security.html)。

### 11. [P2] 本机 frps 没有生成配置历史，回滚功能缺少数据来源

位置：[Apply 的本地分支](E:/Code/git/DFPanel/internal/handler/server.go:288)、[历史查询](E:/Code/git/DFPanel/internal/handler/server.go:518)、[回滚查询](E:/Code/git/DFPanel/internal/handler/server.go:570)。证据：专项复现。

只有 Agent 分支调用 recordConfigVersion，本机应用配置不产生快照。专项测试本机 Apply 返回 200 后，ConfigVersion 表仍为空。对正常本地使用而言，历史页无记录，回滚接口找不到历史版本。

建议：本地与 Agent 共用快照记录逻辑，记录实际应用状态，并在快照持久化失败时停止后续下发。

### 12. [P2] 本机「停止」操作依赖先写配置，磁盘故障会阻止停止

位置：[lifecycle](E:/Code/git/DFPanel/internal/handler/server.go:369)。证据：专项复现。

start、stop、restart 都先生成并写配置。目录丢失、只读、磁盘写满等情况下，stop 直接返回 500，不会走进停止进程的分支。专项测试配置目录无法写入时得到「写入配置失败」；测试未启动生产进程，验证的是控制流提前返回。

建议：停止只依赖实例身份和进程状态，不生成或写配置；是否自动应用尚未生效的编辑，应分别明确启动和重启语义。

### 13. [P2] 历史配置已在面板保存，但远端回滚仍依赖 Agent 本地快照

位置：[节点 Rollback](E:/Code/git/DFPanel/internal/handler/node.go:403)、[回滚 payload](E:/Code/git/DFPanel/internal/handler/node.go:417)、[Agent 读取历史](E:/Code/git/DFPanel/internal/agent/agent.go:289)、[页面提示](E:/Code/git/DFPanel/web/src/components/VersionHistory.vue:43)。证据：代码确认。

面板读取 target.Content 并生成新版本，却只发送 targetVersion。Agent 必须从自己的历史目录找正文。Agent 重装、历史清理或本地数据丢失时，即使面板保存完整快照，离线回滚上线后仍会失败；页面「面板会重新下发」的提示与实际实现不一致。

建议：以面板已保存的配置正文下发回滚任务，或明确只支持 Agent 仍持有的历史版本，更新离线提示及按钮可用条件。保留 payload 兼容策略，避免旧 Agent 误解新格式。

### 14. [P2] 应用配置返回遗漏 unverified，页面会把未确认当成功

位置：[节点 Apply 响应](E:/Code/git/DFPanel/internal/handler/node.go:229)、[服务端 Apply 响应](E:/Code/git/DFPanel/internal/handler/server.go:278)、[节点前端](E:/Code/git/DFPanel/web/src/views/Nodes.vue:522)、[服务端前端](E:/Code/git/DFPanel/web/src/views/ServerConfig.vue:145)。证据：代码确认。

Agent 返回 OK=true、Unverified=true 时，dispatch 正确保留状态并把历史记录设为 unverified，但上述两个 Apply 响应没有输出 unverified。前端警告分支因此进不去，显示绿色成功提示，尽管尚未确认连通。Rollback 响应已有该字段。

建议：统一结果结构，完整返回 ok、running、rolledBack、unverified、queued；让页面与历史状态一致。另需单独决定配置丢失恢复时如何处理 unverified：目前 ManagedConfigs 只恢复 applied，可能恢复更旧配置或不恢复。

### 15. [P2] 删除节点没有删除其隧道与访问端数据

位置：[节点 Delete](E:/Code/git/DFPanel/internal/handler/node.go:168)、[UI 删除承诺](E:/Code/git/DFPanel/web/src/views/Nodes.vue:612)、[数据库迁移](E:/Code/git/DFPanel/internal/database/database.go:26)。证据：专项复现。

Delete 只删除 Node；模型关系和当前迁移不会自动级联清理 Proxy、Visitor。专项测试删除成功后，两类数据行均保留。界面称删除节点及其隧道配置，但数据库存在不可从节点列表管理的孤儿记录，其中可能保留密钥。

建议：在事务中明确删除节点的 Proxy、Visitor，并定义配置历史是否保留及保留多久。不要把可能具有审计用途的历史和指令默认一并删除。

## 后续加固项

- 登录接口没有应用层限速、失败次数控制；应结合实际反向代理配置补齐。JWT 目前只验签与有效期，没有服务端会话撤销机制。
- Agent 列表/Get/Update 直接序列化含 Secret 的模型，与「只在创建/安装时返回」注释不一致。当前都是管理员接口，属于不必要的敏感信息扩散；建议使用专门响应结构并禁止敏感响应缓存。
- 安装命令直接拼接 PublicURL/转发头和 shell 参数，没有对 URL 做完整验证和跨 shell 引号处理。可信配置包含特殊字符会生成损坏指令；攻击者控制未校验转发头、且能让管理员使用对应返回值时存在命令注入风险。建议设置明确可信 PublicURL、校验协议和主机、限制可信反向代理，并分别转义 Bash、PowerShell 和 YAML。
- HTTP Server 没有 ReadHeaderTimeout/IdleTimeout，JSON 正文和 WS 消息缺少统一大小限制；进程日志持续追加，需限制日志大小或轮转，避免资源耗尽。
- nextVersion 采用先读最大版本再加一，ConfigVersion 没有目标/版本唯一约束；并发应用可能生成同号快照，应使用事务性分配和唯一约束。此项本次未做并发专项复现。
